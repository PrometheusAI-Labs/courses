## Module 3: Нативный Rust-бэктест

### Teaching Arc
- **Metaphor:** стенд испытаний двигателя: реальный контроллер подключён к моделируемой нагрузке.
- **Opening hook:** the same native strategy shape can be exercised against simulated venue and ordered data.
- **Key insight:** engine, venue, instrument, data and strategy are explicit assembly steps.
- **Why care:** helps keep Rust authoritative across build, replay, validation and reports.

### Duration

- Format totals: theory 26 min, demo 34 min, practice 40 min, quiz 10 min.

### Learning Outcomes
By the end, the learner can:
1. Name the explicit assembly stages of a native Rust backtest: engine, venue, instrument, ordered data, strategy, run, reports.
2. Separate real strategy logic from simulated venue and replayed market data.
3. Identify invalid evidence: unordered data, missing fees/slippage, look-ahead, and reports generated by an unrelated canonical runtime.
4. Define a reproducible Rust-first experiment with inputs, configuration, outputs, and a pass/fail claim.

### Prerequisites
- Modules 1–2 completed, especially ownership and event-flow boundaries.
- Basic meaning of backtest, fill, fee, and chronological market data.
- Ability to compare an experiment claim with the evidence that would support it.

### Guided Lab — «Соберите испытательный стенд» (22 min)
1. Arrange seven assembly cards in execution order.
2. For each card, label whether it is real logic, simulation, input evidence, or output evidence.
3. Add failure checks for chronology, fees, slippage, warm-up, and deterministic configuration.
4. Produce a run manifest: strategy version, data range, instrument, parameters, seed if applicable, and report paths.

### Independent Assignment (18 min)
Write a test charter for comparing EMA periods 10/20 and 20/50 in the same native Rust harness. Define one hypothesis, controlled inputs, invalidation rules, and report outputs. Do not promote the better historical result directly to live.

### Learner Artifact
- A reproducible Rust backtest charter plus a run manifest and a «real vs simulated» layer map.

### Acceptance Criteria
- Rust owns build, replay, validation, and report production.
- Data ordering and provenance are explicit.
- Venue model assumptions include at least fees and fill/slippage behavior.
- The comparison changes only declared strategy parameters.
- The conclusion is bounded to backtest evidence and does not claim live readiness.

### Instructor Notes
- Keep the engine-test-stand metaphor inside this module only.
- Ask learners to physically point to what is simulated before discussing metrics.
- A high return is not the acceptance criterion; reproducibility and falsifiability are.
- Reject any workflow where Python silently becomes the canonical report generator.
- Transition by asking: «какие риски появляются, когда моделируемая площадка становится настоящей?»
