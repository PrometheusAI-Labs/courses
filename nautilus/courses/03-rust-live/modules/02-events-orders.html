От события к заявке

Котировка запускает цепочку решений, но ни один ранний шаг ещё не доказывает сделку на бирже.

1. Пять служб, одна цепочка

Это похоже на аварийную службу: канал надо зарегистрировать, вызов принять, заявку оформить, проверить допуск и только затем передать исполнителю. Подписка и обработчик — уже две разные границы.

⚠️
Команда — не сделка

submit_order означает «передай намерение дальше». Она не доказывает ни принятие площадкой, ни исполнение.

2. Где код разделяет границы

RUST · ДОСЛОВНО
impl DataActor for MyStrategy {
    fn on_start(&mut self) -> anyhow::Result<()> {
        self.subscribe_quotes(self.instrument_id, None, None);
        Ok(())
    }

    fn on_quote(&mut self, quote: &QuoteTick) -> anyhow::Result<()> {
        let order = self.order().market(
            self.instrument_id,
            OrderSide::Buy,
            self.trade_size,
            None, None, None, None, None, None, None,
        );
        self.submit_order(order, None, None, None)?;
        Ok(())
    }
}
ПО-ЧЕЛОВЕЧЕСКИ

Стратегия обещает работать как получатель данных.

При запуске просит поток котировок выбранного инструмента.

Когда runtime доставит котировку, запускается отдельный обработчик.

Фабрика создаёт рыночную заявку на покупку заданного размера.

Стратегия отправляет команду в торговый конвейер и передаёт ошибку наверх.

Код завершился успешно — но подтверждение площадки всё ещё впереди.

Пример специально прост: покупка на каждой котировке не является безопасной production-логикой. Его задача — показать границы.

5. Лабораторная работа: «Котировка есть, сделки нет»

1
Докажите подписку

Есть ли подтверждение регистрации потока и свежие входящие данные?

2
Докажите callback

Увеличивается ли счётчик обработчика для нужного инструмента?

3
Проверьте risk verdict

Создана ли заявка и разрешил ли её независимый контур риска?

4
Проверьте transport

Есть ли отправка, acknowledgement и последующее событие площадки?

Артефакт: дерево решений с пятью контрольными точками. Приёмка: ни одна ветка не приравнивает создание заявки к fill, а исправление начинается только после наблюдаемого доказательства.

6. Проверка понимания: где оборвалась цепочка?

1. Adapter видит quotes, но счётчик on_quote равен нулю. Что проверять первым?

2. Handler завершился успешно, но dispatch отсутствует. Какое доказательство нужно дальше?

3. Venue прислал acknowledgement. Как сформулировать статус?
